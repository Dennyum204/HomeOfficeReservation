## Desenho de identidade proposto

Três registos de produção, ainda não criados, separam responsabilidades. A separação adicional do conector evita que consentimento Graph passe a ser requisito do login. Configuração por ambiente; redirects HTTPS exatos e sem wildcard. Usar bibliotecas OIDC/MSAL, code flow com PKCE, state e nonce validados. [Fluxo oficial](https://learn.microsoft.com/en-us/entra/identity-platform/v2-oauth2-auth-code-flow).

| Registo | Tipo e scopes | Papel |
|---|---|---|
| API/BFF | Confidencial; expõe `api://<api-client-id>/access_as_user`; login `openid profile` | Login Web e recurso protegido para mobile |
| Flutter | Público; `openid profile offline_access` e o scope da nossa API | Login nativo Android/iOS, sem segredo e sem permissões Graph |
| Conector Outlook | Confidencial; `openid profile offline_access` e `https://graph.microsoft.com/Calendars.ReadWrite` | Consentimento e cache Graph exclusivamente no backend |

Os nomes são papéis de configuração, não aplicações ou endpoints já implementados. O registo separado do probe é temporário e não substitui estes três registos.

Configurar os registos para **Personal Microsoft accounts only** (`signInAudience=PersonalMicrosoftAccount`) e endpoints/discovery `https://login.microsoftonline.com/consumers/v2.0/.well-known/openid-configuration`; MSAL usa authority `https://login.microsoftonline.com/consumers`. A API deve aceitar tokens v2 e o issuer consumer devolvido pela metadata, com `tid=9188040d-6c67-4c5b-b112-36a304b66dad`. Este UUID é público e comum às contas MSA; **não identifica Fernando nem concede acesso**. Só membros admitidos explicitamente podem usar o produto. Papéis empregado/gestor ficam na base de dados, pois app roles Entra não são suportados para utilizadores MSA. Scopes próprios da API são suportados; configurar `access_as_user` e admissão do cliente Flutter. [Validações de account type/scopes](https://learn.microsoft.com/en-us/entra/identity-platform/supported-accounts-validation), [authority MSAL](https://learn.microsoft.com/en-us/entra/identity-platform/msal-client-application-configuration).

A página de configuração MSAL ainda descreve a combinação de audiência mista com authority consumers; a referência de registo/manifest documenta a opção pessoal exclusiva. Preferir esta última; se o portal/biblioteca exigir audiência mista, registar a limitação e continuar a rejeitar contas empresariais no código. Não alargar acesso silenciosamente. Essa configuração concreta e emissão de token para a nossa API ainda não foram ensaiadas.

**React Web:** o browser inicia login no BFF; o backend troca o código e cria sessão com cookie Secure/HttpOnly e política SameSite adequada ao callback OIDC. React usa a mesma origem e proteção anti-CSRF em todas as operações mutáveis, incluindo ligar/desligar calendário. Nada de tokens Microsoft em localStorage, URL ou estado React. O backend autoriza cada membro/objeto; consentir não atribui papéis de gestor.

**Flutter Android/iOS:** usar `flutter_appauth` (versão observada 12.1.0) com AppAuth nativo e browser do sistema, code + PKCE. Configurar discovery do tenant, client ID público, redirect registado e os scopes da API na operação `authorizeAndExchangeCode`; renovar a sessão com `token`/refresh token. Guardar material de sessão da nossa API em Keychain/Keystore através de armazenamento seguro, nunca em preferences/logs. A biblioteca não cria automaticamente a política de armazenamento da aplicação. Registar o redirect AppAuth em **Mobile and desktop applications**, conforme a orientação Microsoft para Flutter, e configurar Android manifest/intent filter e iOS URL Types conforme a biblioteca. URI customizada deve usar esquema próprio em minúsculas; claimed HTTPS exige associação real do domínio nas duas plataformas. Redirects finais dependem do bundle/application ID e domínio, ainda por escolher. [Biblioteca oficial do mantenedor](https://pub.dev/packages/flutter_appauth), [registo de redirects Microsoft](https://learn.microsoft.com/en-us/entra/identity-platform/reply-url).

AppAuth é uma biblioteca de terceiros, não MSAL Microsoft. Não demonstra suporte a políticas de app protection, broker ou device compliance. No alvo pessoal confirmado não se pressupõe Intune corporativo. Se futuramente IT exigir broker/Intune, o caminho passa por MSAL Android e MSAL iOS e, quando exigido, Intune SDK, integrados via platform channels Flutter; rever então a viabilidade. Não foi compilado nem autenticado um cliente Flutter neste estudo. [SSO/broker Microsoft](https://learn.microsoft.com/en-us/entra/identity-platform/mobile-sso-support-overview).

**ASP.NET Core API:** Microsoft.Identity.Web/JWT bearer para mobile; sessão cookie para endpoints BFF explicitamente definidos, sem fallback permissivo entre esquemas. Pedir tokens v2 para a nossa API e validar assinatura, emissor/tenant permitido, validade, `aud` igual ao client ID da API e `scp` contendo `access_as_user`. ID token autentica o cliente OIDC; não autoriza chamadas à API. Access token Graph destina-se ao Graph e nunca é aceite como token desta API. Mapear `(tid, oid)` para membro ativo; não usar email como chave de autorização nem `sub` entre registos diferentes. Acesso a cada empregado/gestor exige autorização de negócio. [Audiences e claims](https://learn.microsoft.com/en-us/entra/identity-platform/access-token-claims-reference), [tratamento de access tokens](https://learn.microsoft.com/en-us/entra/identity-platform/access-tokens).

## Ligar calendário, renovar e voltar a ligar

Login deve funcionar sem Graph. No Web, uma ação explícita com sessão BFF e anti-CSRF inicia o consentimento do **conector**, com callback próprio e estado de utilização única ligado ao membro/sessão. Validar a identidade retornada pelo middleware: `(tid, oid)` tem de corresponder ao membro autenticado. Não aceitar ligação de outra conta ou tenant silenciosamente.

No mobile, abrir no browser do sistema a página HTTPS fixa de ligação. Essa página exige login BFF próprio e mostra a conta a ligar antes do consentimento; não transfere o bearer mobile para o browser. O utilizador deve escolher a mesma conta do mobile. O callback associa apenas a conta confirmada pela sessão BFF; a aplicação móvel consulta o estado **do seu próprio membro** através da API e só mostra sucesso quando esse membro estiver ligado. Um browser autenticado noutra conta não liga o calendário ao membro do mobile. O regresso à app é apenas navegação e não prova de sucesso. Este desenho simples pode exigir um segundo login; uma passagem de sessão otimizada não está implementada nem validada.

Microsoft.Identity.Web/MSAL no backend trata a aquisição incremental de tokens delegados. Usar scopes explícitos no consentimento de calendário; não usar `.default` no login para agregar permissões indevidas. Um access token serve um recurso. Não usar um token mobile como credencial permanente do worker nem implementar renovação manual de refresh tokens. [Web app e APIs downstream](https://learn.microsoft.com/en-us/entra/msidweb/call-downstream-apis/from-web-apps), [scopes/OIDC](https://learn.microsoft.com/en-us/entra/identity-platform/scopes-oidc).

Persistir cache MSAL por ligação/conta, cifrada no servidor, com isolamento entre utilizadores e controlo de concorrência. Proposta: adapter de cache persistente em PostgreSQL; não está implementado. `AddDistributedTokenCaches` é a integração da biblioteca, não cria por si só armazenamento durável; `AddDistributedMemoryCache` não serve para persistência/escala. Ativar cifragem e manter keyring Data Protection partilhado, durável e protegido fora da base de dados, com rotação e acesso restrito. Segredos/certificados dos clientes confidenciais ficam no gestor de segredos do alojamento. Não guardar tokens em auditoria, URLs, logs, push, Git ou clientes. [Cache MSAL .NET](https://learn.microsoft.com/en-us/entra/msal/dotnet/how-to/token-cache-serialization).

O worker pede silenciosamente token à biblioteca antes de Graph; esta renova quando necessário. `invalid_grant`, consentimento retirado ou interação/claims challenge exigida levam a `ReconnectRequired`, suspendendo a ligação e solicitando ação no browser. Distinguir 403 por política/permissão de 429/5xx transitórios; não repetir autenticação indefinidamente. Logout ou apagar cache local não prova revogação no servidor. Reconexão repete consentimento com identidade vinculada, substitui cache e retoma delta/reconciliação. Desligar para jobs/subscrições, elimina cache e disponibilidade importada; mantém o planeamento. [Renovação e revogação](https://learn.microsoft.com/en-us/entra/identity-platform/refresh-tokens).

## Delta, datas e propriedade

Calendário principal, Graph v1.0. Initial delta usa janela fixa e percorre todas as páginas; incremental reutiliza o URL opaco devolvido sem reconstruir parâmetros. Não suporta `$select`, `$filter`, `$expand`, `$orderby` ou `$search`; descartar imediatamente campos privados recebidos. O probe valida origem HTTPS e caminho antes de enviar bearer e limita páginas/ciclos. Produção deve persistir projeção+checkpoint de forma consistente, repetir páginas idempotentemente, reinicializar cursor inválido/410 sem interpretar resposta parcial como calendário vazio e abrir janela nova ao avançar horizonte. [Delta oficial](https://learn.microsoft.com/en-us/graph/api/event-delta?view=graph-rest-1.0).

All-day usa meia-noite local até à meia-noite seguinte, mesma zona; datas não passam por UTC. Fixtures usam `GMT Standard Time` para Lisboa e `W. Europe Standard Time` para Zurique; aliases/roundtrip são hipótese a ensaiar no Graph. O calendário expandido inclui ocorrências e exceções; comparar `seriesMasterId` e datas. O probe cria duas séries diárias com três ocorrências sobre a transição de março; exceções editadas/canceladas e séries complexas permanecem fora do ensaio atual. [Event/all-day](https://learn.microsoft.com/en-us/graph/api/resources/event?view=graph-rest-1.0), [instances](https://learn.microsoft.com/en-us/graph/api/event-list-instances?view=graph-rest-1.0), [recurrence range](https://learn.microsoft.com/en-us/graph/api/resources/recurrencerange?view=graph-rest-1.0), [zonas suportadas](https://learn.microsoft.com/en-us/graph/api/outlookuser-supportedtimezones?view=graph-rest-1.0).

Probe publica sem attendees/online meeting/reminder, privado e `showAs=free`. Guarda intenção antes do POST com transaction ID e marcador aleatório; só altera IDs do journal cuja leitura confirma marcador, transaction ID e ausência de attendees. Recupera POST ambíguo apenas por esses identificadores, nunca pelo título. Usa IDs imutáveis em todos os pedidos. [Criar](https://learn.microsoft.com/en-us/graph/api/user-post-events?view=graph-rest-1.0), [extended property](https://learn.microsoft.com/en-us/graph/api/singlevaluelegacyextendedproperty-get?view=graph-rest-1.0), [IDs imutáveis](https://learn.microsoft.com/en-us/graph/outlook-immutable-id).

PATCH/DELETE enviam `If-Match` com ETag lido; a documentação específica dos endpoints não demonstra a garantia de concorrência que pretendemos. O suporte/412 real continua por testar; não retirar a precondição automaticamente perante erro. Não editar em simultâneo os eventos de teste. Adicionar attendees manualmente faz o probe recusar mutação; cancelar uma reunião pode enviar mensagens, pelo que esse cenário requer intervenção privada do operador, nunca limpeza arbitrária. [Atualizar](https://learn.microsoft.com/en-us/graph/api/event-update?view=graph-rest-1.0), [Eliminar](https://learn.microsoft.com/en-us/graph/api/event-delete?view=graph-rest-1.0).

## Subscrições e infraestrutura para validação posterior

Proposta para implementação posterior: subscrição básica, sem rich resource data, `changeType=created,updated,deleted`, recurso `me/events`, permissionamento delegado da ligação e `Prefer: IdType="ImmutableId"` na criação. O sinal pode abranger eventos além do calendário principal; nunca seguir arbitrariamente um resource URL recebido. Validar subscrição/ligação/clientState e agendar delta do calendário principal. `clientState` aleatório fica protegido no backend e é comparado de forma segura. Endpoints notification/lifecycle precisam de HTTPS público estável, TLS válido e acesso externo Microsoft. Nenhum domínio foi escolhido ou publicado.

Na validação, devolver o `validationToken` descodificado como texto simples, HTTP 200, em até 10 segundos, sem o registar. Nas notificações normais, persistir trabalho e responder 202 rapidamente (objetivo menos de 3 segundos), ou 200 se já processado; falha de persistência devolve 5xx. Microsoft pode repetir entregas até quatro horas; atrasos prolongados podem provocar perda de notificações. Fila durável, deduplicação/coalescência, métricas sem payload e delta periódico são obrigatórios. [Entrega webhook](https://learn.microsoft.com/en-us/graph/change-notifications-delivery-webhooks).

O máximo documentado de Outlook básico é 10 080 minutos; rich notifications têm limite inferior, 1 440 minutos. Pedir seis dias e guardar a expiração efetivamente devolvida; renovar diariamente e garantir margem de pelo menos 24 horas, com lease para evitar renovações concorrentes. Estes intervalos são decisão operacional proposta, não SLA Microsoft. Se renovação falhar, retry com backoff/Retry-After até à margem; alertar, recriar após expiração e reconciliar delta. [Subscription](https://learn.microsoft.com/en-us/graph/api/resources/subscription?view=graph-rest-1.0).

`reauthorizationRequired` exige reautorizar/renovar conforme a API e pode exigir reconexão do utilizador; `subscriptionRemoved` exige recriar e reconciliar; `missed` exige delta. Manter reconciliação periódica proposta de 15 minutos mesmo sem sinal, e recuperação de cursor inválido. Testes futuros: validação endpoint, clientState inválido, duplicados, indisponibilidade/fila cheia, renovação, expiração, lifecycle e delta após perda. [Lifecycle](https://learn.microsoft.com/en-us/graph/change-notifications-lifecycle-events).

Infraestrutura em falta: acesso ao diretório de registo, registos/consentimento e mailbox dedicada; para webhooks, hostname HTTPS de staging, serviço sempre ativo, PostgreSQL/fila, chave de cifragem e scheduler. Não foram criadas subscrições, não foi testada entrega nem escolhida hospedagem. O probe local precisa apenas de browser/loopback e acesso HTTPS direto; não valida webhook nem resolve o alojamento de produção.
